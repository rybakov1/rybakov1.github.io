# Эксплуатация

## VPS

Для небольшой демоинсталляции достаточно одного Linux VPS с Docker Compose; точный объём памяти/CPU зависит от нагрузки и размера фидов. Не требуется Kubernetes. Установите актуальные Docker Engine и Compose, создайте отдельного непривилегированного пользователя и скопируйте исходники/`.env` безопасным способом. Секреты не храните в Git и образах.

Сначала запустите проект локально на VPS через `docker compose up --build -d` и проверьте `docker compose ps`, `/health`, каталог, карточку, импорт и админку. Затем поставьте Caddy/nginx с HTTPS перед `127.0.0.1:3000` и API `127.0.0.1:8000`. Откройте только необходимые публичные порты 80/443; PostgreSQL не публикуйте.

Укажите настоящий origin в `PUBLIC_BASE_URL`, `PUBLIC_SITE_URL`, `CORS_ORIGINS` и адрес API в `PUBLIC_API_URL`; внутренний `API_BASE_URL` оставьте `http://backend:8000`. Браузер должен обращаться к доступному HTTPS API, а не к контейнерному имени `backend`. После смены публичных переменных пересоберите frontend. Базовые URL для canonical/sitemap должны совпадать с выбранным публичным доменом.

До открытия доступа замените PostgreSQL-пароль и `ADMIN_TOKEN`, настройте защиту админского маршрута/ограничение попыток на reverse proxy, проверьте разрешённые домены переходов, договоры источников и политику хранения. Не включайте реальный источник простым снятием демобейджа. Демокаталог не является производственными данными.

## Резервное копирование PostgreSQL

Ниже Linux-команды на хосте VPS. Сохраняйте копии вне VPS с ограниченными правами и шифрованием. Потоковый редирект бинарного дампа особенно в старом Windows PowerShell может изменить байты; для Windows сначала создайте файл внутри контейнера и копируйте через `docker compose cp`.

```sh
mkdir -p backups
docker compose exec -T db pg_dump -U cenoscope -d cenoscope -Fc > backups/cenoscope.dump
```

В PowerShell безопасно перенесите готовый файл без бинарного редиректа:

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
docker compose exec db pg_dump -U cenoscope -d cenoscope -Fc -f /tmp/cenoscope.dump
docker compose cp db:/tmp/cenoscope.dump backups/cenoscope.dump
```

Восстановление нужно регулярно проверять на отдельной тестовой БД. Следующая команда перезаписывает содержимое указанной базы и предназначена только для согласованной процедуры восстановления:

```sh
docker compose exec -T db pg_restore -U cenoscope -d cenoscope --clean --if-exists < backups/cenoscope.dump
```

Вместе с БД сохраняйте версию исходников/образов, список миграций и конфигурацию. Ключ `TELEGRAM_ID_ENCRYPTION_KEY` храните отдельно от дампа. Потеря ключа делает сохранённые Telegram ID недоступными; публикация ключа вместе с дампом снимает защиту шифрования. Токен бота при утечке отзывайте и заменяйте.

## Обновления

Перед изменением схемы сделайте резервную копию и проверьте миграции на тестовой БД. Соберите новую версию, выполните штатный запуск с `alembic upgrade head`, проверьте `/health` и ключевые пользовательские действия. Сохраните предыдущие образы. Откат кода не обязательно совместим с новой схемой: решение об откате миграции/восстановлении принимается отдельно.

## Диагностика

- `docker compose ps` показывает состояние служб; `docker compose logs --tail 100 backend frontend db` — недавние ошибки.
- API не стартует: проверьте `db` healthcheck, `DATABASE_URL`, пароль и вывод Alembic. Ошибка миграции не должна маскироваться созданием пустой схемы.
- Каталог показывает только демо: проверьте доступность `API_BASE_URL` из frontend-контейнера и наличие данных в БД. Встроенный деморежим сохраняет UI, но не подтверждает успешное соединение с backend.
- Админка недоступна: проверьте, задан ли `ADMIN_TOKEN`, и передаётся ли актуальный токен. Не выводите его в публичные логи и снимки экрана.
- Импорт отклонён: проверьте формат, время наблюдения с часовым поясом, обязательные поля, валюту/условия и журнал запуска. Не отключайте валидацию ради загрузки.
- Бот отключён: задайте токен, имя и ключ шифрования; запустите профиль `telegram`. Один polling-процесс на токен. Проверьте явное подтверждение подписки и cooldown, прежде чем считать отсутствие сообщения ошибкой.
- Запускайте один экземпляр worker. Дедупликация и cooldown уменьшают повторы, но авария после отправки Telegram до записи результата допускает повторную доставку. Worker без токена всё равно выполняет очистку по срокам хранения.
- Внешний переход заблокирован: проверьте домен в разрешённом списке. Не разрешайте произвольный URL или редирект-параметр.
- График/отзывы пусты: отсутствие достаточных наблюдений корректно отображается как недостаток данных; не дополняйте реальную историю синтетикой.

## Наблюдение и сроки хранения

Следите за временем последнего успешного импорта, числом отклонённых строк, свежестью наблюдений, ошибками Bot API и ростом БД. Конкретную частоту обновления задаёт разрешение источника. Ошибки не должны сохранять секреты/полные пользовательские сообщения. Настройте исполнение политики удаления и проверяйте, что резервные копии не хранят персональные данные бессрочно.

Публичный запуск требует отдельной проверки реального провайдера, HTTPS, политики конфиденциальности, прав на данные/изображения/отзывы, канонических URL, запрета индексации тонких страниц и восстановления из копии. Эта инструкция не утверждает, что такая проверка уже выполнена.
