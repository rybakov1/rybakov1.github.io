# Архитектура

## Компоненты

`frontend/` — Astro с Node SSR-адаптером и типизированным клиентом. Страницы каталога и модели доступны по читаемым URL; интерактивные фильтры, выбор периода, отзывы и подписка работают в браузере. Имя сервиса и базовый URL задаются переменными окружения. Встроенный демокаталог позволяет показать интерфейс при отсутствии API; он явно помечен и не заменяет постоянное хранилище. Отдельная статическая сборка демо через `EXPORT_STATIC=1` предназначена для демонстрации интерфейса, основной Compose-запуск использует серверный режим.

`backend/` — FastAPI с OpenAPI, SQLAlchemy, Alembic, провайдерами, расчётами и Telegram-интеграцией. Для production используется PostgreSQL, для локальной разработки допустим SQLite. API не начинает краулинг при запуске. Импорт запускается оператором с указанием разрешённого источника.

`infra/` — два Dockerfile, а `docker-compose.yml` — PostgreSQL, API, сайт, worker и опциональный bot. Redis, Kubernetes и отдельные микросервисы не нужны. Worker очищает служебные данные и при наличии настроек проверяет активные персональные подписки. Бот использует polling; инфраструктура не содержит канального постинга.

## Путь данных

DemoProvider или разрешённый ImportProvider формируют модели, офферы и наблюдения с происхождением. После валидации записи попадают в БД, где уникальные ключи предотвращают повторные наблюдения. Сервис аналитики строит равномерные дневные срезы и сравнивает только одинаковые условия предложения. API отдаёт каталог, карточку, историю и срезы отзывов. Фронтенд помечает демо, показывает дату наблюдения и не выдаёт данные за текущие предложения площадок.

При создании алерта сохраняется ожидающее подтверждения намерение, а deep link открывает личный бот. Только действие пользователя в боте активирует подписку. Worker повторно проверяет условие, исключает повторную доставку и отправляет сообщение через Bot API. Персональные идентификаторы не попадают в фронтенд и шифруются в хранилище.

## Основные сущности

- Канонические модели и варианты: бренд, нормализованная модель, MPN/GTIN при наличии, ключевые характеристики, состояние, комплектность. Объём памяти и Ti-суффикс — существенные признаки, не украшения имени.
- Продавцы и офферы: отдельные идентификаторы, условия гарантии/оплаты, площадка, внешняя ссылка, происхождение. Оценка продавца, рейтинг товара и вычисляемая надёжность оффера имеют разные значения.
- Наблюдения цен: сумма, валюта, регион, тип цены, условие оплаты, доступность, время наблюдения и источник. Дневные значения не зависят от числа событий изменения цены.
- Отзывы/агрегаты: вариант, источник, выборка, период, число оценок, доступные признаки. Синтетические записи допустимы только в явном деморежиме. Реальные тексты требуют разрешения.
- Совпадения моделей: уровень уверенности и очередь ручной проверки спорных пар.
- Запуски синхронизации: источник, статус, время, счётчики, ошибка и основание доступа.
- Подписки: целевая цена, согласие, защищённый идентификатор получателя, состояние, последняя отправка/дедупликация.
- Служебная аналитика: тип события, продукт/оффер, время; минимальный набор данных без выдуманных кликов.

Актуальный состав таблиц, индексы и ограничения задаёт `backend/app/models.py` и миграции Alembic. Менять схему следует миграциями, а не созданием таблиц вручную в работающей БД.

## Разделение доверия

Секрет администратора и ключи Telegram доступны только backend. `PUBLIC_*` попадают в браузер и не должны содержать секреты. Админские операции требуют токена, внешние переходы разрешены только для известных доменов, URL из импорта не загружаются автоматически. Производственный фронтенд и API следует публиковать за HTTPS reverse proxy.

Реальные источники подключаются через `MarketplaceProvider`, не через обработчики страницы. Замена импортёра на Go/Rust позже возможна при сохранении схемы наблюдений и происхождения. Сначала следует измерить скорость на реальном разрешённом фиде: сеть и качество данных часто важнее языка парсера.
